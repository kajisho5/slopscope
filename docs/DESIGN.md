# slopscope 設計書 v0.1

ホームページのデザインを「見た目」と「数字」の両方で監査する Agent Skill。

- 作成日：2026-11-06
- 状態：**オーナー承認済み（2026-11-06、§11 はすべておすすめで決定）。v0.1.0 として実装**

---

## 1. 名前

**リポジトリ名・スキル名：`slopscope`**（オーナー決定 2026-11-06）

- 意味：AI っぽい雑さ（slop）を「見る道具（scope）」。直す unslop に対して、測って見る役割を名前に出した。
- GitHub での同名は 5 件（最大★1、別用途）。スキル名の規則（小文字・数字・ハイフン、64 字以内）を満たす。
- 最初の案 `mekiki`（目利き）から変更。

## 2. 何をするスキルか（要件）

### 2.1 目的

公開中の URL、または手元の HTML・コードを渡すと、次の 2 段で監査する。

1. **見た目の監査（目で見る）：** AI が作ったっぽい特徴、まとまりのなさ、文言の誇張を、画面を見て指摘する。unslop の考え方を参考にするが、文章は自分で書く。
2. **計測（数字で見る）：** ブラウザで実際に開いて、文字の見やすさ、キーボードで選んだときの枠、スマホでのはみ出しなどを数字で出す。KATA UI で作って使っている測り方を、どのサイトにも使える形にする。

最後に、直す前と後の画像を比べて、「良くしたら壊れた」を防ぐ。

### 2.2 しないこと

- 自動で直すことはしない。直すのは、オーナーが「直して」と言ったときだけ。方向性の提案 → 確認 → 修正、の順を守る。
- 有料の画像生成は使わない。v1 では入れない。
- 「デザインとして良い」とは言い切らない。数字で測れることと、意見を分けて書く。
- スクリーンリーダー、実機、Safari・Firefox での確認の代わりにはならない。報告の最後に、毎回「確かめていないこと」として書く。

### 2.3 使う場面

- **作った直後：** AI に作らせたホームページや LP を、公開する前に見る。
- **直した後：** 直す前と後を比べて、見やすさや操作性が悪くなっていないか確かめる。
- **よそのサイト：** 他社サイトを見て、自分のサイトとの差を知る。ただし計測だけで、コードは触らない。

### 2.4 既存のスキルとの違い

| スキル | 対象 | 方法 | slopscope との違い |
|---|---|---|---|
| unslop | Web 画面 | AI が見て方向性を出し、9 段階で直す | slopscope は計測と前後比較が主役。直すのは頼まれたときだけ |
| design-check-skill（あなたの環境にあるもの） | Apple のアプリ（iPhone・iPad・Mac・Watch） | 項目表で「抜け」を探す | 対象が Apple のアプリで、Web ではない |
| web-design-guidelines（Vercel） | Web のコード | ガイドラインを取りに行き、コードを読んで指摘する | ブラウザで開いて測ることはしない |
| accessibility-review | デザイン・ページ | WCAG の項目を目で確認する | 数字での計測はない |

## 3. 監査の中身

### 3.1 見た目の監査（目で見る・意見）

画面を撮った画像とコードを見て、次の項目を「場所」と「理由」付きで 1 行ずつ書く。点数は付けない。

| ID | 見るもの | 例 |
|---|---|---|
| V-01 | 色 | 紫系のグラデーション、光るぼかし、色付きの影、アクセント色が多すぎる |
| V-02 | 余白 | 同じ種類のものの間隔がばらばら、4px の倍数になっていない |
| V-03 | 文字 | 太さの種類が多すぎる、小さい文字に詰めた字間、すべて大文字のラベル |
| V-04 | アイコン | 絵文字をラベル代わりに使っている、線の太さや大きさがそろっていない |
| V-05 | 文言 | 「！」の多用、誇大な言葉（革新的、次世代）、根拠のない数字 |
| V-06 | 配置 | 主なボタンが 2 つ以上ある、何もない帯、どの商品でも通用する型どおりの構成 |
| V-07 | 動き | ずっと動き続けるもの、跳ねる動き、動きを減らす設定に従わないもの |

日本語サイト向けの項目（unslop にはない）：

| ID | 見るもの |
|---|---|
| V-08 | 和文と欧文の文字の大きさや太さが合っていない、全角と半角が混ざっている |
| V-09 | 本文の行の高さが詰まりすぎている（和文は 1.7 前後が目安） |

### 3.2 計測（数字で見る・事実）

ブラウザ（Chromium）で開いて測る。すべての項目に「基準」「測り方」「どこが外れたか」を付ける。

| ID | 測るもの | 基準 | 測り方（KATA で使っているもの） |
|---|---|---|---|
| M-01 | 文字の見やすさ | 4.5:1 以上（大きい文字は 3:1）WCAG 1.4.3 | 画面の画素から計算（文字の色と背景の色を実際の表示から取る） |
| M-02 | キーボードで選んだときの枠 | 選んだときに見た目が変わる WCAG 2.4.7（v0.2 で訂正。前後 3:1 は AAA の 2.4.13 なので「弱い」として目で確かめる） | Tab で 1 つずつ移り、選ぶ前と後の画像を比べる |
| M-03 | 枠の欠け | 親要素に切られていない | 枠の広がりと、親の「はみ出し非表示」を比べる |
| M-04 | スマホでの横はみ出し | 幅 375px で横スクロールしない | はみ出した要素の名前と、はみ出した幅（px）を出す |
| M-05 | iPhone の入力時の拡大 | 入力欄の文字が 16px 以上 | 幅 375px で、すべての入力欄の文字サイズを測る |
| M-06 | 名前のない操作部品 | 入力欄・ボタン・リンクに名前がある | ブラウザの「名前の計算」の結果を見る |
| M-07 | 押せる大きさ | 24×24px 以上 WCAG 2.5.8 | 押せる要素の大きさを測る |
| M-08 | 動きを減らす設定 | 設定が有効なとき、ずっと続く動きが止まる | 設定をまねて、動いている要素を数える |
| M-09 | 値のばらつき | （基準なし・参考） | 使われている色・文字サイズ・余白の種類を数えて、多い順に並べる |

M-09 は KATA の「型の検査」の代わりになるもの。トークン（共通の値）がないサイトでも、ばらつきが見える。

### 3.3 前後比較

- 直す前と後で、同じページを同じ幅（375px と 1280px）・同じテーマ（ライト・ダーク）で撮る。
- 画素の違いがあった範囲を出す。
- M-01〜M-08 の結果を並べて、悪くなった項目を一番上に出す。

## 4. 流れ

1. **対象を受け取る：** URL か、手元の HTML・フォルダ。
2. **画面を撮る：** 幅 375px と 1280px、ライトとダークで撮る。ダークは、サイトが対応している場合だけ。
3. **計測する：** `scripts/measure.py` で M-01〜M-09 を測る。
4. **見た目を監査する：** V-01〜V-09 を、画像とコードを見て判定する。
5. **報告を書く：** 事実（計測）と意見（見た目）を分けて書く。
6. **止まる：** 直す方向性を 3〜5 行で提案し、オーナーの確認を待つ。
7. **直す（頼まれたときだけ）：** 直したら手順 2〜3 をやり直し、`scripts/compare.py` で前後を比べる。

## 5. 技術選定

### 5.1 計測の道具（候補の比較）

| | **A. Python＋Playwright（おすすめ）** | B. Node.js＋Playwright | C. Lighthouse を呼ぶ |
|---|---|---|---|
| 動作の軽さ | 普通（ブラウザ 1 つを動かす） | 普通 | 重い（独自の計測を多く走らせる） |
| 配布サイズ | スキル本体は数十 KB。Chromium は別に必要 | 同じ | Lighthouse 自体が大きい |
| 作りやすさ | KATA で動いている測り方（Python）をそのまま移せる | 書き直しが必要 | M-02（枠が見えるか）のような独自の測り方は作れない |
| 対応 OS | Linux・Mac・Windows（Claude Code が動く所） | 同じ | 同じ |
| 将来性 | Playwright は Microsoft が継続的に更新している | 同じ | 得点は出るが、項目を自由に足せない |
| AI での書きやすさ | 高い。公式仕様でも、補助のスクリプトに Python が挙げられている | 高い | 設定が複雑 |

**おすすめは A。** あなたの技術選定ルールで、Agent Skill の補助スクリプトは「Python か bash」となっています。また、KATA UI の `verify_focus_ring.py` などがすでに Python で動いて実績があります。

### 5.2 使うもののバージョン（2026-11-06 確認）

| もの | バージョン | 根拠 |
|---|---|---|
| Agent Skills の SKILL.md 仕様 | 公式仕様。必須は `name`・`description`。任意は `license`・`compatibility`・`metadata`・`allowed-tools`（試験段階） | https://agentskills.io/specification |
| Playwright for Python | 1.64.1（2026-10-22）。Python 3.10 以上 | https://pypi.org/project/playwright/ |
| Pillow（画像の比較） | 13.0.0（2026-10-16）。Python 3.11 以上 | https://pypi.org/project/pillow/ |
| Python | 3.11 以上（Pillow 13 の条件に合わせる） | 同上 |

- Claude Code だけで使える項目（`disable-model-invocation` など）は使わない。公式の基本仕様の項目だけで書くので、Claude Code と Codex の両方で動く想定。
- 名前の判定（M-06）に axe-core を使う案もある。ただし最新版を確認できなかった（npm の公式ページが取得できなかった）ので、v1 では入れない。ブラウザ自身の「名前の計算」を使う。

## 7. データの形（measure.json）

```json
{
  "target": "https://example.invalid/",
  "measured_at": "2026-11-06T10:00:00+09:00",
  "browser": "Chromium 156",
  "viewports": [375, 1280],
  "themes": ["light", "dark"],
  "checks": [
    {
      "id": "M-01",
      "status": "fail",
      "threshold": "4.5:1",
      "findings": [
        {"selector": ".hero p", "viewport": 375, "theme": "light", "value": "3.2:1", "box": [16, 220, 343, 48]}
      ]
    }
  ],
  "not_verified": ["screen readers", "Safari", "Firefox", "real devices"]
}
```

- `status` は `pass`・`fail`・`info` のどれか。M-09 だけは `info`（参考）。
- 前後比較は、この JSON を 2 つ並べて差を出す。

## 8. 報告の形（report.md）

1. **まとめ：** 3 行以内。測った項目の合格数、目立つ問題の上位 3 つ。
2. **計測（事実）：** M-01〜M-09。外れた所を、場所・数字・画像付きで出す。
3. **見た目（意見）：** V-01〜V-09。場所と理由を 1 行ずつ。
4. **直す方向性の提案：** 3〜5 行。ここで止まって確認を待つ。
5. **確かめていないこと：** 毎回必ず書く。

報告は Markdown にして、画面の部品（UI）は作らない。そのため、あなたのルールの Step 2（SVG デザイン）は対象外と考えている。HTML の見やすい報告ページが欲しい場合は、Step 2 で SVG を作ってから進める。

## 9. 確かめ方（テスト）

- `examples/` に 2 ページ置く。「問題をわざと入れたページ」と「直したページ」で、会社名や中身は明らかに架空のものにする。
- `tests/` で次を確かめる。
  - 問題を入れたページで、M-01〜M-08 がそれぞれ 1 件以上「不合格」になる
  - 直したページでは 0 件になる
- GitHub Actions（Linux）で、変更のたびに自動で流す。Mac は使わない前提。
- 公式の検査ツール `skills-ref validate` で、SKILL.md の形が正しいか確かめる。

## 10. 確かめていないこと・わからないこと

- **claude.ai のチャット上でのスキル実行：** Chromium が使えるかは確認していない（**不明**）。v1 は Claude Code と Codex を対象にし、README に書く。
- **unslop の細かい項目一覧（`references/signs.md`）：** まだ読んでいない。参考にするときは、ライセンス（CC BY 4.0）にしたがって作者名とリンクを書く。文章は写さず、自分で書く。
- **あなたの環境にある design-check-skill：** 先頭だけ読んだ。Apple のアプリ向けなので重ならないと判断したが、全文は読んでいない。

## 12. v0.2 の変更（実在のサイトで試してわかったこと）

2026-11-05 に、実在の公開サイト 6 つ（example.com、python.org、W3C WAI、デジタル庁、react.dev、GOV.UK）と、新しい見本 `examples/tricky.html` で試した。v0.1 で見つかった問題と直し方：

| 問題 | 起きたこと | 直し方 |
|---|---|---|
| 画面外の文字で止まる | 画面の外に置いた読み上げ用の文字や、スライドショーの 2 枚目があると、計測全体がエラーで止まった | 見える部分だけを測り、画面の外の文字は飛ばす |
| サイトの安全設定で止まる | GOV.UK は、外から足したスタイルを禁止する設定（CSP）のため止まった | 計測用のスタイルだけは許す設定で開く |
| 隠れたメニューで誤った不合格 | 右から出るメニューを閉じて隠しているだけで、横はみ出し（M-04）と押す大きさ（M-07）が不合格になった | 本当に横にスクロールできるかをブラウザに聞く。隠れた部品は数えない |
| 同じ形の部品でキー操作の確認が途中で止まる | 名前の指定（セレクタ）が短くて重なり、3 つのカードのうち 1 つ目で止まった | 必ず 1 つに決まる名前を作る。同じ要素かどうかは要素そのもので見る |
| 部品の中（Web コンポーネント）を見ない | 部品の中の薄い文字や名前のないボタンを見落とした | 部品の中まで調べる（名前は ` >>> ` で区切る） |
| 読み上げ用に隠した文字を 1:1 と判定 | W3C とデジタル庁で、見えない見出しが不合格になった | 切り抜かれて見えない文字は測らない |
| ふわっと出る文字を薄いと判定 | 動きを「最初の状態」で止めていたので、透明に近い状態で測っていた | 終わる動きは最後まで進めてから測る。ずっと続く動きだけ最初で止める |
| 画面外の部分が真っ白 | react.dev は、画面外の描画を省く設定（content-visibility）のため、白地に白と判定された | 計測のときは全部描かせる |
| 測っている間にページが動く | python.org は上の画像の切り替えで高さが 24px 変わり、文字の位置がずれて、読みやすい日付が 1.54:1 と判定された | ページの時計（タイマー）を止め、撮る直前に位置を測り直す |
| 枠の基準が厳しすぎた | 「前後で 3:1 変わる」は WCAG 2.2 の 2.4.13（AAA）の基準だった。W3C の黄色く変わるボタンが不合格になった | 何も変わらないときだけ不合格。変わり方が弱いものは画像を保存して目で確かめる |
| 文中の小さいリンクを不合格 | python.org の著作権表示の行のリンクが、押す大きさ不足とされた | まわりにリンク以外の文があれば、文中のリンクとして除く |
| 2 行に折り返したリンク | 折り返したリンクの外枠が隣を覆い、「近すぎる」と誤判定した | 行ごとの枠で距離を測る |
| ダークモードの判定 | 設計書では「対応している場合だけ」だったが、いつも 2 回測っていた。画像の比較では、動く広告などで「対応している」と誤判定した | 使われている色の一覧を比べる。対応していなければ明るい方だけ測る（時間も半分） |
| スキルを入れても動かない | `requirements.txt` がスキルのフォルダの外にあり、スクリプトの場所も「scripts/」としか書いていなかった | どちらもスキルのフォルダの中で完結させた |

追加したもの：表示の遅いページを待つ、下までスクロールして後から出る中身を出す、`--click`（クッキーの同意画面を閉じる）、`--wait`、ボット対策の画面やエラー画面の警告、長いページを 1 画面ずつに分けた画像、M-01 の色の組ごとのまとめ、直し方の手引き（`references/fix-playbook.md`）。
